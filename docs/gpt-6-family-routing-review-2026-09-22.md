# Four-model Codex routing assessment

Reviewed September 22, 2026 for Work Router 1.8.1 and UI Router 1.17.1. This refines
the earlier Sol/Luna release review: Astra has a direct task-based role, not merely an
exception for existing sessions. Work Router owns model/effort choices; UI Router owns
the design method and acceptance evidence.

## Adopted policy

| Model | Default role | Boundary |
|---|---|---|
| GPT-6 Luna | Narrow implementation, mechanical changes, bounded inventories and extraction with objective checks | Return ambiguity or consequential judgment to a capable parent; do not delegate trivial work merely to use a cheaper family. |
| GPT-5.6 Terra | Conditional independent reading when user preference or workload evidence warrants it | Verify availability; do not invent Terra 6, infer retirement, or assume an automatic cost/latency advantage. |
| GPT-6 Sol | Substantial everyday reasoning, difficult implementation, architecture, diagnosis, synthesis and integration | A strong default does not establish superiority on every difficult task. |
| GPT-6 Astra | Hardest cross-system judgment, unresolved creative/spatial direction when maximum quality matters, or demonstrated Sol capability limits | Select it directly when warranted; no mandatory failed Sol/max attempt, and no automatic max/ultra setting. |

Preserve useful context, explicit model choices, one writer per working tree, and
Standard service. Model recommendations do not switch a running parent. Optional
delegation must repay startup, context, review and integration costs.

## Evidence and uncertainty

The [dated evidence basis](../plugins/work-router/skills/route-ai-work/references/routing-basis.md)
records current official model guidance, named benchmark versions and efforts, API
rates, and the limits of those measurements. It preserves historical GPT-5.6 rows under
their actual version. Sources include the [current model guide](https://developers.openai.com/api/docs/guides/latest-model),
[Astra release](https://openai.com/index/gpt-6-astra/),
[Sol/Luna release](https://openai.com/index/introducing-gpt-6-sol-and-luna/), and
[Terra 5.6 model page](https://developers.openai.com/api/docs/models/gpt-5.6-terra).

Terra remains documented as 5.6. Current API rates give Sol 6 the same input rate and a
lower output rate than Terra 5.6; that weakens a blanket price-based Terra route but
does not prove a lower completed-task cost or shorter Codex latency. No direct current
Terra-versus-Sol-6/Luna-6 benchmark was verified for the proposed reading role.

The Astra-versus-Sol design result published with Astra compares **Sol 5.6**, not Sol 6.
Coding and computer-workflow benchmarks support a capability distinction but do not
rank visual taste. No verified current four-model visual-quality or matched wall-clock
experiment determines the best route for every task. Representative rendered work,
accepted outcomes and rework remain stronger local evidence than a promotional demo.

## Policy checks

- A well-specified multi-file feature can stay with Sol; Astra availability alone
  does not require escalation.
- An unusually difficult diagnosis or quality-first spatial design can start with
  Astra; a failed cheaper attempt is not a prerequisite.
- A one-line UI correction stays with its capable parent; Luna is not mandatory.
- A bounded source inventory can use Luna; a requested or workload-proven Terra 5.6
  reader remains valid. Judgment-heavy conclusions return to Sol or Astra.
- Missing inputs require better inputs; more model capability is not the first fix.
- An explicit family constraint applies to children. Unsupported models/settings
  require a disclosed compatible fallback, never a silent substitution.
- A polished screenshot with an untested primary action remains unaccepted, regardless
  of which model produced it.

These are policy exercises, not a comparative execution benchmark. Revisit the routing
when official guidance or host support changes, or representative accepted work supplies
comparable quality, elapsed-time, retry and review evidence.
