# Maintaining skills from evidence

Use this when a source, bookmark, user correction, or observed failure suggests a skill
change. A saved post is a research lead, not a standing instruction or an endorsement.

## Decide what belongs

1. Read the original claim and relevant follow-up. Separate an observed result from a
   proposed experiment, promotion, or second-hand summary. Record the source date and
   review date; preserve which author actually recommended a tool.
2. Separate durable methods from volatile details. Check current model, harness,
   configuration, license, pricing and installation facts upstream. Old evidence can
   still support a method; a new leaderboard result does not establish the best route
   for every task. Compare like tasks, harnesses, settings, and total completion cost.
3. Identify the decision the change would improve and the existing instruction that
   owns it. Choose: **adopt**, **conditional**, **already covered**, **reference only**,
   **defer**, or **reject**. Missing evidence should remain missing, not become policy.
4. Make the smallest reusable correction. State when it applies, when it does not,
   what counts as success, and what would justify revisiting it. Prefer one focused
   reference over a new broad skill or repeated rules across every plugin.
5. Check a realistic applicable case and a nearby case that should not trigger it.
   Check conflicts with user intent, current routing, ownership and permissions.
   Distinguish policy review from an actual behavioral trial or comparative benchmark.

Retain only selected public source links and generic reasoning in the repository.
Do not publish a user's bookmark archive, saved-item status, private annotations,
account details, or unrelated personal interests. Do not copy an external prompt or
skill wholesale without reviewing its scope and license.

## Carry a release through

- Work in the canonical checkout; inspect its instructions, dirty files and remote.
- Update each changed plugin's two manifests, Claude marketplace version, changelog,
  and any affected discovery data or field-guide version. Codex marketplace entries
  that resolve versions from plugin manifests do not need invented version fields.
- Run the relevant package checks and inspect the diff. Stage only intended files,
  commit, and make a normal push within the maintainer's authorized update scope.
  Reconcile remote changes without discarding others' work or force-pushing.
- Verify the published commit. Refresh requested installed copies from that release
  using the current host's supported plugin commands and verify version/content.
  Keep the persistent marketplace pointed at its canonical source.
- Report **published**, **installed**, and **loaded** separately. An active session may
  retain earlier skill instructions until reload or a new task. Do not claim an update
  is automatic unless the actual sync mechanism has been inspected and verified.
