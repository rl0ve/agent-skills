# Visual complexity modes

Use this reference to choose how visually ambitious a deck should be before building it.

Choose the deck archetype first. Visual complexity should intensify that archetype, not replace it.

## Default
- If the user does not specify a preference, use `standard`.

## Modes

### Minimal
- Use when speed, clarity, or editability matters most.
- Favor template-native layouts, simple icon support, short bullets, and straightforward charts.
- Avoid elaborate compositions unless a single diagram is necessary.

### Standard
- Use for most customer and internal decks.
- Mix text, icons, simple diagrams, screenshots, and clean charts as needed.
- Favor one strong visual idea per slide and avoid empty decorative space.

### Rich
- Use when the deck should feel more premium, strategic, or visually persuasive.
- Increase the use of vector diagrams, mixed media, stronger hierarchy, annotated screenshots, logo ecosystems, and image-led moments.
- Allow more bespoke compositions when they improve narrative flow, but keep them inside the chosen deck archetype.

### Showpiece
- Use when the user explicitly wants a high-design result for executive, keynote, launch, or marquee storytelling.
- Combine strong typography, bold composition, layered vector systems, editorial image treatment, and custom diagrams.
- Keep polish extremely high and reserve extra time for QA.
- Even here, do not let every slide become a separate visual experiment.

## Archetype interaction

- `case-study system`: richer modes should upgrade the recurring frame, proof modules, mini-diagrams, and cover polish without abandoning repetition.
- `executive narrative`: richer modes can support stronger covers, section moments, and one or two standout slides, but the deck should still rely on a small family of slide types.
- `product proof`: richer modes should improve screenshot treatment, callout design, and surrounding narrative context rather than replacing evidence with abstract art.
- `platform architecture`: richer modes should deepen diagram craft, layering, legends, and editorial framing while keeping the system map language consistent.

## Visual medium selection
- Use native shapes for process diagrams, layered architectures, swimlanes, comparisons, and operating models.
- Use SVG/vector art for icons, product symbols, logos, connector maps, and clean explanatory diagrams.
- Use screenshots for product proof, workflow evidence, and interface walkthroughs.
- Use charts and tables for quantified claims.
- Use photos or illustrations for emotion, context, or section-setting slides.
- Use hybrid compositions when the slide needs both proof and explanation.

## When to ask the user
- Ask directly when visual ambition is likely to change layout density, media sourcing, or build time.
- If the user already hints at the preference with words like `simple`, `premium`, `visual`, `executive`, `image-heavy`, `diagram-heavy`, or `showpiece`, treat that as the answer.
- Ask or infer the asset sourcing policy when screenshots, photos, or illustrations matter: use provided/local assets first unless the user clearly wants newly generated or externally sourced imagery.

## Anti-pattern
- Do not reduce every deck to the same box-and-bullet system.
- Do not add photos or graphics just for decoration; each medium should earn its place.
- Do not fabricate UI proof or pseudo-screenshots when authentic product visuals are unavailable.
- Do not use `rich` or `showpiece` as permission to vary layout language on every slide.
