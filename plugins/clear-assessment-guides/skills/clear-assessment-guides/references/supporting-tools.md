# Supporting skills and tools

Choose the explanation and delivery mode first, then select a collaborator for a
concrete job. Check the target host's current skill catalog and actual callable tools;
a familiar name, directory or marketplace listing does not prove availability. Read
any selected skill's instructions before using it. This package neither bundles nor
installs the collaborators below. Use an available simpler route when a collaborator
is missing; investigate installation only if it materially helps and is authorized.

Preserve the user's audience, facts, requested format and scope. Supporting tools must
not silently turn a content assessment into a redesign, a document into a website, or
a review into an editing assignment. Keep essential explanation beside its evidence.
Apply the chosen mode's quality checks; a collaborator's default aesthetic does not
override the actual project brief.

## Diagram Design for relationships and structural comparisons

Look for `diagram-design` or an available Diagram Design plugin. Use it for current-state
maps, process relationships, handoffs, architecture or structural before/after change.
Select the meaning before the layout. Align unchanged nodes across a before/after pair
so the difference is visible. Retain editable source, such as vector/native shapes or
the supported diagram source, beside the rendered asset. Verify the selected tool's
actual formats; HTML/SVG output does not imply editable presentation shapes.

Skip a diagram for a simple list or a change consisting only of a label, attribute or
sentence. Use a compact table or before/after text instead. If Diagram Design is not
available, an existing diagram editor, supported diagram notation or simple editable
vector shapes can serve the task. Do not install a dependency merely to draw boxes.
Use supplied style requirements when the selected workflow supports them; do not alter
an installed skill's global defaults to match one project.

## Visual Explainer when HTML helps understanding

Look for `visual-explainer`. Use it when a standalone HTML explanation, comparison or
visual mechanism materially improves the reader's understanding and fits the destination.
It can support an explanation; the assessment skill still owns findings, evidence,
review decisions and their distinction from live execution. For feedback collection,
preserve the [interactive review contract](interactive-review.md).

Do not default to animation, a slide deck, a website or an elaborate layout. A static
HTML explanation is often enough. Keep essential reasoning visible for the selected
issue and independently readable in any requested document/print export. Do not claim
an HTML file is offline or portable without checking dependencies and destination
behavior. If HTML does not help or necessary tooling is unavailable, keep the requested
document or annotated screenshot rather than forcing a format change.

## doc-coauthoring for explanation and fresh-reader clarity

Look for `doc-coauthoring` when collaboratively developing a substantial assessment,
proposal or guide. Its useful jobs are gathering missing context, refining structure
and checking whether an unfamiliar reader can understand the result. Reuse supplied
context and authorized sources before asking questions. When audience and requirements
are clear, avoid imposing a questionnaire, brainstorming loop or extra approval ceremony.
Honor the user's choice of structured co-authoring or freeform drafting.

Before delivery, check whether a reader without the conversation can identify the
current experience, task, problem, impact, proposed change, evidence, status and next
action. For a guide, check whether they can follow the steps and recognize success.
Use an independent fresh reader when available, useful and authorized; give that reader
the artifact and realistic reader questions, without coaching them with the intended
answer. If only the author can review it, call it a self-review, not an independent
reader test. Record unresolved gaps rather than inventing missing context.

If unavailable, draft directly and apply the same clarity questions. A final prose
editor such as Natural Writing can improve wording when appropriate; keep one final
editor and do not repeat multiple humanizing passes. Co-authoring owns structure and
reader comprehension, not an additional serial style-cleanup process for every paragraph.

## Document and PDF tools for the actual deliverable

Use the available document workflow for editable documents, PDF tools for inspection
or export, and presentation tools only for requested or genuinely presented slides.
Resolve current names, runtimes and capabilities from the host rather than embedding
machine-specific commands. Use the relevant connected native-document integration if
that is the requested destination.

These tools construct and verify the file; they do not decide that every assessment
needs slides. A PDF alone does not establish an editable source. Render and inspect
all final pages or slides for clipping, readable type, borders, image-caption proximity,
table breaks and links. Verify the actual export, not only the authoring source. State
any unavailable rendering or export checks plainly.

## Product Design only for an actual interface task

Use an available product-design workflow when the task requires an interface audit or
prototype. It is distinct from Diagram Design and is not required to explain a content
assessment. Keep review findings separate from implementation. A simple content brief
can use the document and relationship-diagram routes above.

## Image generation only for necessary illustration

Use an available image-generation tool only when a necessary illustration cannot be
served by a screenshot, diagram or existing asset. Resolve the actual provider and
instructions; similarly named integrations are not interchangeable. Label illustrations
and proposed mockups clearly. Never generate or reconstruct factual screenshot
evidence. Native annotations or overlays should preserve the original pixels. If art
is nonessential or the capability is missing, omit it rather than delay the assessment.

## Video and motion only when sequence matters

Use a short GIF or clip for an interaction whose sequence or state changes cannot be
explained clearly by a still. A substantial requested walkthrough may warrant an
available workflow using HyperFrames, Remotion or another suitable tool. Verify and
read the selected integration before promising formats, narration or portability.
Do not assume the tools are interchangeable or installed.

Do not turn a concise brief into an animation or narrated deck by default. A numbered
screenshot sequence or static sequence diagram is a useful alternative, including for
readers who cannot comfortably watch motion. Keep observed behavior separate from
proposed behavior in either medium.
